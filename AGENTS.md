# AGENTS.md

Personal collection of agent skills plus the scripts that install them and the surrounding harness. Read this before changing or running anything here.

## Layout

| Path | Purpose |
|------|---------|
| `skills/<name>/SKILL.md` | The repo's own skills (plus optional `assets/`, `references/`) |
| `external/catalog.tsv` | Third-party skill repositories that can be installed on demand |
| `setup.sh` | Single entry point: menu and `--only` over the three scripts below |
| `install.sh` | Installs this repo's skills by family into Claude Code and Cursor |
| `install-external.sh` | Installs catalog entries into every harness detected on the machine |
| `bootstrap-harness.sh` | Installs and configures T3 Code, Claude Code, Codex, Cursor CLI, Gentle AI, Engram |
| `odd/tasks/<feature>.md` | Tracking document for substantial work |
| `docs/` | Per-area documentation |

`.atl/` is generated by Gentle AI (skill registry). Never commit it.

## Installing: always ask first

Never install, update or configure anything without an explicit selection from the user.

1. Run `./setup.sh --list` (or `--list tools|external|families`).
2. Ask which items the user wants.
3. Run `./setup.sh --only <ids> --yes` (add `--dry-run` to preview).

Without a terminal, `setup.sh`, `install.sh` and `install-external.sh` exit with code 2 if no selection is given. `bootstrap-harness.sh` without `--only` acts on its default set (T3, Gentle AI, Engram and the CLIs in `--agents`) after asking for confirmation, so pass `--only` when calling it directly.

| Group | Examples | Handled by |
|-------|----------|------------|
| Tools | `t3`, `claude-code`, `codex`, `cursor`, `gentle-ai`, `engram` | `bootstrap-harness.sh` |
| External skills | `diagram-design` | `install-external.sh` |
| Skill families | `kubernetes`, `datadog`, `ops`, `productivity`, `harness` | `install.sh` |

Families are mapped by skill name in `skill_family()` in `install.sh`; a new skill that matches no pattern falls into `other`.

## Harness detection

Scripts install only where a harness exists and report the rest.

- `install.sh`: Claude Code (`claude` or `~/.claude`), Cursor (`cursor-agent` or `~/.cursor`).
- `install-external.sh`: Claude Code, Cursor, Gemini CLI, OpenCode, GitHub Copilot, Codex, Windsurf. The table lives in `harness_table()`; add a harness there only after checking its global skills directory in the `skills` CLI README.
- `bootstrap-harness.sh configure` targets only agents whose CLI is installed.

## External skills

- A catalog line is `id`, `owner/repo`, skills (comma-separated or `*`), license, description, separated by tabs.
- They are third-party: they add instructions, and sometimes scripts, that agents follow. Review a repository before listing it, show source and license before installing, and require confirmation.
- Installation goes through `npx skills@<pinned version>` (`SKILLS_CLI_VERSION` in `install-external.sh`). Bump the pin deliberately, not automatically.
- Verify a repository's skill names read-only with `npx --yes skills@<version> add <owner/repo> --list`.
- The `skills` CLI has no check-only update mode, so latest versions are reported as `unknown`.

## Writing skills

- Write `SKILL.md` in English.
- Follow the skill-creator style guide: frontmatter (`name`, one-line quoted `description` of at most 250 characters starting with `Trigger:`, `license`, `metadata.author`, `metadata.version`), then Activation Contract, Hard Rules, Decision Gates, Execution Steps, Output Contract, References. Keep the body under 1000 tokens and move detail to `assets/` or `references/`.
- `install.sh` treats any file containing `{{UPPER_CASE}}` as a placeholder template and installs a rendered copy instead of a symlink. Do not write that pattern literally in scripts or docs inside a skill.
- Register a new skill in `README.md` and `.claude-plugin/marketplace.json`.

## Shell conventions

- `bootstrap-harness.sh` sets `IFS` to newline and tab. Split lists with `IFS=',' read -r -a`, not by unquoted expansion.
- `install.sh` and `setup.sh` run with `set -euo pipefail`. A function whose last command may legitimately fail must end with `return 0`.
- No test runner exists. Verify with `bash -n <script>`, `--dry-run`, and `--list`. Do not run real installs to test.

## Workflow

- Branch off `main`; do not commit to `main`.
- Conventional commits, one per work unit, with docs alongside behavior. No AI attribution lines.
- For work with two or more steps, create `odd/tasks/<feature>.md` before the first change and keep it updated.
- The user decides pushes, pull requests and merges.
